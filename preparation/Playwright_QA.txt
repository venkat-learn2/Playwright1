9.What are the different locators strategies?
        > page.getByRole() to locate by explicit and implicit accessibility attributes.
        >page.getByText() to locate by text content.
        >page.getByLabel() to locate a form control by associated label's text.
        >page.getByPlaceholder() to locate an input by placeholder.
        >page.getByAltText() to locate an element, usually image, by its text alternative.
        >page.getByTitle() to locate an element by its title attribute.
        >page.getByTestId() 
        > Also use CSS and Xpath selectors

16. What is browser , context , page in playwright?
        
        >Browser = Apartment Building
        Context = Individual Flat
        Page = Room inside the flat

        > BROWSER - A browser instance that Playwright launches. - example: Chromium,Chrome,firefox
        > const browser = await chromium.launch();
        > One browser may have many contexts

        > BROWSER CONTEXT - A fresh isolated session inside the browser.
            > Each context has:    
                Separate cookies    
                Separate cache    
                Separate storage    
                Separate login session

            👉 Works like Incognito window.

        > const context = await browser.newContext();

        > Multiple users testing simultaneously

        > Parallel execution

        > No session conflict

        > - PAGE - A single browser tab where automation happens.

            > This is where you:

               > Click

               > Type    

               > Navigate

               > Assert
        const page = await context.newPage();
        await page.goto("https://example.com");       

        > Playwright uses browser contexts to provide test isolation without launching multiple browsers, which improves performance

32.Assertions in playwright
        1.Generic Assertions - Value Based 
                >toBe() - Exact Match - expect(value).toBe(10);
                > toEqual() - Deep Equality(object/array) - expect(obj).toEqual({id:1})
                > toContain() - Partial Match Text  - expect(text).contain('success')
                > toBeTruthy()/ toBeFalsy() - expect(isActive).toBeTruthy()
                > toBeNull() - expect(value).toBeNull
                > toBeGreaterThan() / toBeLessThan() - expect(count).toBeGreaterThan(5)

        2. Location Assertios - these are auto waiting assertions 
                > tobeVisible() - await page.expect(locator).tobeVisible();
                > tobeHidden() - await page.expect(locator).tobeHidden();
                > toHaveText() - await page.expect(locator).toHaveText('expected') - exact text 
                > toContainText() - await expect(locator).toContainText() - partial text matches 
                > toHaveCount() - await expect(locator).toHaveCount(10) - count 
                > toHaveAttribute() - await expect(locator).toHaveAttribute('type',text);
                > toHaveCSS() - await expect(locator).toHaveCSS("color":"rgb(0,0,0)");
                > toHaveClass() - await expect(locator).toHaveClass("active")
                > toBeEnabled() - await expect(locator).toBeEnabled() 
                > toBeDisabled() - await expect(locator).toBeDisabled()
                > toBeChecked() - await expect(locator).toBeChecked()
                > toBeFocused() - await expect(locator).toBeFocused()

        3.Page Assertions
                > toHaveURL() - await expect(page).toHaveURL('htttps://example.com/');
                > toHaveTitle() - await expect(page).toHaveTitle("Dahsboard");

36.What is a Flaky Test?

        > A Flaky tests is a test , sometimes passes , sometimes failes without any code changes 
        > mainly caused by timing issues , network delays , dynamic elements , test data conflicts , environment instability
        Root cause: will check step by step 
        First, I identify the root cause instead of increasing timeouts. 
        Most flaky tests are due to synchronization issues, unstable locators, or test data conflicts. 
        I rely on Playwright’s auto-waiting assertions, proper network waits, and stable selectors like data-testid. 
        I ensure tests are independent and parallel-safe. As a last step, I use retries in CI,
         but only after fixing the root issue. My goal is to make tests deterministic and reliable.

        > Identify flaky tests by analyzing test results over time and looking for patterns of failure.

        > Use logging and screenshots to gather more information about the test failures.

        > Implement retries for tests that fail intermittently, but limit the number of retries to avoid masking issues.

        > Refactor tests to isolate dependencies and reduce environmental factors that may cause flakiness.

        > Collaborate with developers to understand the application behavior and address underlying issues.
